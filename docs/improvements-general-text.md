# General document text capture

The `Document text` card (`?mode=text`) captures an upright printed page
hands-free, using the same outline, quality, stability and perspective
correction as proof of address. Uploaded photos use the same reader. The camera
is released before OCR; leaving while OCR runs suppresses the late result and
completion events.

## API

`Scanner.text_page(rgba, width, height)` (wasm) and
`Scanner::text_page_native` (Rust) return:

- `text`: lines joined with newlines;
- `words`: text, `x`, `y`, `w`, `h`, and zero-based `line`;
- `lines`: text and bounding rectangles;
- `page_size`: dimensions of the enhanced, deskewed coordinate space;
- `timings_ms`: enhancement and OCR times.

Input must be an upright, flattened RGBA page. The caller can find and flatten
it with `page` and `flatten`. The reader retains the existing 1754-pixel page
processing budget and the strip detector (tile fallback if that optional model
is absent), then recognises complete lines. This avoids shrinking all of a
page's small print into the ID reader's fixed detection input. The existing
`text` API is retained, with its original output and cost.

`docscan:text` fires once after a live capture, carrying `result`, `imageUrl`
and `blob`, followed by `docscan:complete`. Photo uploads produce results but
do not fire live-capture events. The result screen offers plain-text copying
and copying the complete JSON with word positions.

Coordinates are **not** coordinates on the original photo or the smaller JPEG
preview. Reading order is row-based with gaps split into separate lines; this
is not semantic table recognition or paragraph ordering across columns. The
underlying OCR recognises the Latin alphabet. Blank/unreadable pages return
empty text, not a claim of successful extraction.

## Reproducible DEV measurement

The fixture generator and scorer were committed before the new reader. All
12 pages are synthetic: prose and invoice layouts, three font sizes, with and
without uneven illumination. No personal documents, TEST data, or trained
weights were used to choose the implementation. The two paths run through the
same native binary and models. This is a development smoke corpus, **not a
representative real-world benchmark**.

```
PATH="$HOME/.cargo/bin:$PATH" cargo build --release --manifest-path docscan/Cargo.toml --example text
/tmp/docscan-bench/venv/bin/python eval/text_eval.py --binary docscan/target/release/examples/text
```

Raw result: `eval/results/general-text-dev-v1.json` (fixture and binary hashes,
per-page errors and times). Normalised case-insensitive alphanumeric scoring:

| Metric | Existing text reader | New page reader |
| --- | ---: | ---: |
| Character error rate | 5.12% | 0.29% |
| Word recall | 92.67% | 99.11% |
| Extra words | 28 | 3 |
| Mean native latency | 1.23 s | 2.58 s |

The accuracy gain costs about twice the CPU time in this run. These timing
passes are sequential on a shared machine, not an interleaved latency study;
do not treat their ratio as a statistically established speed result. No
existing scanner is switched to this slower path.

## Research context and next measurements

The upstream [ocrs engine](https://github.com/robertknight/ocrs) separates
word detection, line grouping and recognition. Its own documentation describes
it as a preview with more errors than commercial engines. The current
[RT-DocLayout paper](https://arxiv.org/abs/2606.23344) motivates measuring
geometric rectification and reading order separately from transcription.
Neither source establishes quality for this implementation. A larger held-out
corpus of consented real pages, multiple columns, tables, thermal receipts,
rotation, curved pages and phone measurements is still required. The ocrs path reuses its existing models. The optional PP-OCRv6 tiny reader
uses separate Apache-2.0 models and does not add a VLM dependency.

## Browser checks

After rebuilding wasm, refreshing `scripts/fetch-models.sh`, and building the
demo, run `cd demo && node e2e/text.mjs`. The test covers a small-print upload,
versioned model caching, hands-free capture, one completion event, released
camera tracks, and leaving while OCR is pending. Synthetic fixtures are
regenerated by the DEV command above. Browser checks do not replace testing on
physical phones.

Model download URLs now contain a hash of the served model bytes, computed at
build time. Updated tagger/OCR/face weights therefore do not remain hidden
behind an older Cache API entry on a returning visitor's device. This is cache
versioning, not a security or model-authenticity guarantee.


## Optional PP-OCRv6 tiny reader

The Document text card also offers PP-OCRv6 tiny. A deep link is
`?mode=text&textEngine=ppocr_v6_tiny`. The existing ocrs page reader remains the
default. The optional reader runs in Rust/RTen in the same WebAssembly worker;
Python and ONNX Runtime are used only by the development experiment.

`PaddleTextScanner` loads the pinned detector, recognizer and full CTC
dictionary; its `read(rgba, width, height)` returns `text`, `lines` (confidence,
quadrilateral and bounding rectangle), `page_size`, `timings_ms` and
`engine: "ppocr_v6_tiny"`. Its coordinates refer to the original **input page**,
which is normally the flattened capture. It does not invent word boxes.
The ocrs reader's coordinates instead refer to its enhanced/deskewed page.
The result screen labels this difference when copying structured output.

The two ONNX files total 6,243,229 bytes; the dictionary is about 41 KB.
`scripts/ppocr-v6-models.json` pins the official revisions, sizes and SHA-256.
Build-time model fetching verifies these before publishing same-origin assets;
the browser downloads them only on the first selected PP-OCRv6 read. Loading a
page or using another scanner does not fetch the optional models. Model URLs
are content-versioned like the other readers.

The pinned model publishes multilingual capability; the fixed DEV experiment
here covers only 12 simple English pages. Model configuration and RTen/ONNX
Runtime comparison are recorded under `experiments/ppocr_v6/`. This is an
optional reader for comparison, not a replacement for the ID checks or PoA
field tagger. No multilingual, handwriting, real-document or phone-performance
claim follows from the English smoke corpus.


### Browser smoke for the optional engine

The combined build passed `demo/e2e/text.mjs` with
`DOCSCAN_TEXT_ENGINE=ppocr_v6_tiny`, on both one and two wasm threads. The
small-print photo was read, all three optional assets were fetched only when
used, camera capture emitted one completion and stopped its tracks, and
leaving during a pending read suppressed that capture's events.

On the synthetic bank-statement camera clip, the optional reader reported
5.24 s / 114.1 MiB allocated wasm memory with one thread and 3.87 s / 118.2 MiB
with two. These are individual headless desktop Chrome measurements under
shared load, **not** a calibrated speed comparison or total browser RAM, and
not measurements on a phone. GitHub Pages uses the single-threaded build.

### Upload navigation regression

The additional browser case starts a text photo read and opens another
scanner before it completes. The old App component failed: photo completion
replaced the new camera screen. The App now aborts publication of pending
uploads on opening a scanner, returning home, or browser Back/Forward, and
revokes discarded result image URLs. Worker computation can finish, but its
late result cannot change the newer screen or push history. The browser test
observes the worker's text response before asserting that the new camera
remains, so it cannot pass merely because OCR has not finished yet.


## External-data follow-up and small print

The long-line guard now bounds the recognition tensor at 3200 pixels wide
instead of rejecting a complete page containing a longer line. The native and
WebAssembly regression uses a pinned publisher-synthetic bank statement.

`PaddleTextScanner.read_detailed(rgba, width, height)` (native:
`read_detailed_native`, CLI: `text_v6 --detail`) compares the standard 960-pixel
and detailed 1600-pixel detector caps. The page reading with more alphanumeric
characters weighted by decoder confidence wins; ties retain standard. It is a
coverage heuristic, not calibrated accuracy. Input already within 960 pixels
uses one pass. Output includes `passes` and `detection_max_side`; timings include
both passes. Normal `read` remains single-pass with the original cap.

Select **PP-OCRv6 tiny · small print** on the text card or use
`?mode=text&textEngine=ppocr_v6_tiny_detail`. Upload and camera capture share the
request helper and retain cancellation behavior. No extra weights download.
The preset uses more compute and memory: the regression bank page allocated
about 201 MiB of wasm memory versus about 85 MiB with the standard pass. This is
allocated linear memory on desktop, not peak process RSS or a phone benchmark.

The external DEV study covers 50 FATURA invoices and ten Bankstatemently pages,
with a separate 400-invoice training subset acquired but not used for fitting.
The final profile recovers 2497/2639 bank tokens (94.62%) at 96.93% precision;
standard recovers 2336/2639 (88.52%) at 96.41%. One page loses two matched tokens;
seven improve; invoice results are unchanged. The twelve synthetic regression
pages remain at zero normalized CER. Full protocols, provenance, rejected
candidates and limitations are in `experiments/public_documents/RESULTS.md`.
